# ADR-0001：以 App Manifest 和 Runtime 作为应用接入边界

- 状态：已接受
- 日期：2026-08-28
- 关联 Spec：`docs/specs/SPEC-20260828-p1-app-platform.md`
- 取代：无
- 被取代：无

## 背景

应用展示信息、动态加载器和桌面手工接线分散，新增应用的修改点会随平台能力增加而继续增长。

## 决策

使用本地 TypeScript App Manifest 作为应用静态声明的单一权威来源；使用 React Context Runtime 暴露桌面会话能力。Manifest 不做远程发现，Runtime 不复制桌面状态，应用专属领域 Props 允许继续由外壳适配并逐步迁移。

## 备选方案

### 继续维护独立清单

- 优点：改动最少；
- 缺点：每增加一种平台能力就增加一处手工登记；
- 未选择原因：一致性测试只能发现遗漏，不能消除重复来源。

### 自动扫描目录或微前端插件

- 优点：应用隔离程度更高；
- 缺点：增加构建、类型和运行时复杂度；
- 未选择原因：当前全部应用同仓、同版本发布，不需要远程发现能力。

## 影响

### 正向影响

- 新平台字段可以在统一应用声明中扩展；
- 应用可按需使用桌面运行时，不必持续增加顶层 Props。

### 代价与限制

- Manifest 仍是编译期本地清单；
- 不会立即消除全部手工应用适配代码。

### 对现有能力的影响

- 数据与迁移：无；
- 应用接入：元数据和 loader 统一声明；
- 测试：继续使用清单契约测试；
- 构建与部署：保持现有动态 import 和发布路径。

## 实施边界

- 本决策要求修改：注册表、loader 来源和最小 Runtime；
- 本决策不要求修改：应用领域组件、存储、资源包、多实例和远程插件。

## 验证方式

- TypeScript 推导、清单一致性单测和全部单测。

## 后续决策

- Storage Provider 和资源包字段由各自 Spec 扩展 Manifest 或平台注册表。
