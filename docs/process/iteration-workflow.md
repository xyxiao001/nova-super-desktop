# NOVA Spec 驱动迭代流程

## 目的

这套流程用于在应用和游戏持续增加时控制需求范围、架构影响和交付质量。流程保持轻量：小型单点修改可以直接实施；新增能力、跨应用改动和架构决策必须先留下可追踪的 Spec。

标准闭环：

```text
提出目标
  → 编写轻量 Spec
  → 确认范围与“不修改边界”
  → 拆成单目标迭代
  → 实现和验证
  → 对照 Spec 审计 diff
  → 记录 ADR 和后续事项
```

## 何时需要 Spec

| 变更类型 | 要求 |
| --- | --- |
| 文案、样式、小 Bug、明确的单点修改 | 在任务中写清目标和不修改边界，可不单独建 Spec |
| 新应用、新游戏、跨应用工作流、存储或离线行为变化 | 必须创建 Feature Spec |
| 应用契约、窗口系统、文件模型、持久化、Service Worker 等长期架构决策 | 必须创建 Feature Spec；决策接受后补充 ADR |

不确定时，满足以下任一条件就创建 Spec：

- 需要修改三个及以上业务文件；
- 涉及用户数据、备份、恢复、清理或迁移；
- 涉及多个应用或桌面外壳；
- 会改变后续应用的接入方式；
- 验收标准无法用一句话说清。

## 文档位置与命名

```text
docs/
├── specs/                  # 需求与设计范围
├── iterations/             # 单目标实施记录
└── adrs/                   # 已接受的长期架构决策
```

- Spec：`SPEC-YYYYMMDD-short-name.md`
- 迭代：`ITER-YYYYMMDD-short-name-NN.md`
- ADR：`ADR-NNNN-short-name.md`

`short-name` 使用小写英文和连字符。文档建立后不因标题调整而反复改名。

## 阶段与准入条件

### 1. 提出目标

用一个可验证的结果描述目标，不在目标中混入实现方案或顺手优化。

进入下一阶段前必须明确：

- 当前可复现的问题或要获得的能力；
- 用户或系统能观察到的完成结果；
- 本次目标只有一个中心主题。

### 2. 编写轻量 Spec

复制 `docs/specs/TEMPLATE.md`，填写背景、目标、非目标、现状证据、方案、平台影响、验收标准和风险。

Spec 描述“要实现什么”和必要的设计约束，不记录逐行编码计划。未知事项必须显式列入待确认项，不使用隐含假设补齐。

### 3. 确认范围与不修改边界

Spec 状态从 `草稿` 变为 `已接受` 前，需求提出者必须明确确认：

- 目标和用户可感知行为；
- 本次新增行为；
- 不修改的行为、数据和文件边界；
- 验收标准；
- 已知迁移或兼容影响。

实现中发现必须增加兜底、校验、兼容分支、重试、迁移或其他超范围行为时，停止当前实现，按照仓库组训重新确认范围；不得把实现困难当作默认授权。

### 4. 拆成单目标迭代

复制 `docs/iterations/TEMPLATE.md`。每个迭代只交付一个可独立验证的目标，并引用所属 Spec 和对应验收条目。

拆分原则：

- 优先先建立契约和测试，再迁移实现；
- 行为保持型重构与新功能分开；
- 数据迁移与 UI 变化分开；
- 单次最多进行三轮“实现—验证”循环；
- 未进入当前迭代的事项保留在 Spec 的后续事项中。

### 5. 实现和验证

只修改迭代记录列出的范围。验证与风险相匹配，默认包括：

```bash
npx tsc --noEmit
npm run test:unit -- <相关测试>
```

- 默认不运行 lint；仅在用户当次明确要求时运行。
- 默认不运行完整构建；仅在用户明确要求或当前迭代本身属于构建、部署链路时运行。
- 新行为优先增加相关单测；跨应用和窗口行为应增加相应集成验证。
- 验证失败时记录现象和下一轮假设，不扩大需求范围。

### 6. 对照 Spec 审计 diff

交付前逐项检查：

- 每一处修改都能对应当前迭代目标；
- Spec 验收条目有验证证据；
- 没有新增未获授权的兜底、校验、兼容或重构；
- 没有改变 Spec 标记为“不修改”的行为；
- 没有把用户数据复制到第二套存储；
- 新应用数据已考虑备份、恢复、清理和资源生命周期；
- 工作区中的用户原有修改没有被覆盖。

建议使用只读检查：

```bash
git status --short
git diff --check
git diff --stat
git diff
```

### 7. 记录 ADR 和后续事项

当本次迭代形成会长期约束后续开发的决策时，复制 `docs/adrs/TEMPLATE.md`。ADR 只记录已经接受的决策，不把未确定方案写成既成事实。

以下情况通常需要 ADR：

- 引入或替换核心抽象；
- 改变数据所有权或持久化模型；
- 改变应用接入、窗口或资源生命周期；
- 选择一条主要构建或部署路径；
- 做出难以逆转且影响多个模块的技术取舍。

未完成但仍有价值的事项写回 Spec 的“后续事项”，不得在当前 diff 中顺手实现。

## 状态约定

### Spec

`草稿` → `评审中` → `已接受` → `已完成`

不再实施的 Spec 标记为 `已取消`；被新 Spec 替代时标记为 `已取代` 并链接替代文档。

### 迭代

`待开始` → `进行中` → `已完成`

无法在三轮实现—验证内完成时标记为 `受阻`，记录阻塞证据和需要的决策。

### ADR

`提议` → `已接受`

后续决策改变时，原 ADR 标记为 `已废弃` 或 `已取代`，保留历史记录。

## 完成定义

一次迭代只有同时满足以下条件才算完成：

- 当前迭代目标已经实现；
- 对应验收标准全部通过；
- TypeScript 检查和相关测试通过，或已明确记录未执行原因；
- diff 审计完成且没有超范围改动；
- 用户可感知变化、验证结果和未实现事项已记录；
- 必要的 ADR 已建立，后续事项已回写 Spec。
